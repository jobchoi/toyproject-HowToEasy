# 개발 환경·재사용 구조·API 없는 플랫폼 자동화

2026-10-26 / 설계 제안. 환경을 새로 설치하거나 구현을 완료했다는 기록이 아니다. 진행 체크는 ../TASKS.md에서 관리한다.

## 실제 저장소 구성

기존 frontend는 React + Vite의 App.jsx/main.jsx를 사용하는 JavaScript 구성이다. @types/react 설치만으로 TypeScript 프로젝트가 되는 것은 아니다. 기존 backend는 Python/FastAPI다. 하나의 저장소에 여러 영역을 둔 형태이며 워크스페이스·공유 패키지·통합 빌드 도구를 갖춘 모노레포 체계는 확인하지 않았다. 기존 영역은 그대로 보존한다.

## 추천 환경

- 로컬 개발: WSL + 독립 Python .venv + 고정 의존성. 앱을 Conda base 환경에서 직접 실행하지 않는다. Conda로 설치한 Python을 기반 인터프리터로 쓰는 것은 가능하나 같은 프로젝트에서 Conda/pip 환경을 여러 겹 관리할 이유는 현재 적다.
- 현재 .venv는 system-site-packages로 준비를 시도했던 실험 환경이고 .venv-browser는 브라우저 시험 환경이다. 삭제하지 않고 사용 여부를 확인한 뒤 재현 가능한 독립 환경으로 정리한다.
- pyproject.toml로 의존성과 도구 설정을 관리하고 잠금 파일 또는 완전 고정 의존성 파일을 함께 둔다. 설치 도구는 처음엔 venv+pip로 충분하며 도구 교체 자체를 선행 과제로 만들지 않는다.
- 서버 배포: 기능이 검증되면 Docker로 Python·OS 라이브러리·실행 명령을 묶는다. venv는 Python 패키지 격리, Docker는 OS 사용자 공간까지 포함한 실행 환경 패키징이므로 대체재만은 아니다.
- 사용자 로그인 브라우저: 첫 시험은 로컬에서 실행한다. 서버 컨테이너가 사용자 PC 크롬을 자동 제어할 수 있다고 가정하지 않는다. 현재 /tmp 브라우저·라이브러리는 다른 환경에 보장되지 않으므로 설치 스크립트로 재현해야 한다.
- Conda는 과학 계산·GPU 라이브러리 등 구체 요구가 생기면 재평가한다. 이번 게시 도구에서 필수로 추가하지 않는다.

## Python에서 해볼 학습 과제

컴포넌트 재사용 경험을 서비스·데이터 계약·어댑터 재사용으로 확장한다. MVC 폴더를 만드는 것보다 한 기능이 CLI·웹·테스트에서 같은 코드로 실행되는 것을 목표로 한다.

1. dataclass/Pydantic으로 Article/ContentBlock/Image/Citation 같은 데이터 계약을 만든다.
2. 순수 변환 함수로 Markdown/블록을 미리보기와 내보내기에 재사용한다.
3. Service가 검토·게시 규칙을 처리하고 Controller는 요청/응답만 담당하게 한다.
4. Protocol 등으로 게시 경계를 정의하고 모의 플랫폼과 네이버 브라우저 구현을 교체한다. 플랫폼별 임시저장/사진/결과조회 지원을 capability로 구분한다.
5. SQLite Repository와 메모리 테스트 구현으로 저장 로직을 분리하고 중복·버전 충돌·재시작 실패를 검사한다.
6. CLI와 FastAPI를 같은 Service에 연결한다. 공통 코드가 실제로 필요한 두 소비자를 가질 때 별도 패키지를 추출한다.

초기에는 posting-automation 내부 Python 패키지 하나로 충분하다. 향후 apps/web, apps/browser-helper, packages/publishing-core 같은 배치는 공통 기능과 별도 실행 주체가 실제 생긴 뒤 도입한다. 지금 빈 패키지나 별도 서버를 늘리지 않는다.

## API가 없을 때의 인터페이스

JSON/XML은 데이터 형식, 파일/표준입출력/소켓/HTTP는 전달 경로, 브라우저 DOM은 조작 대상이다. 우리 프로그램 사이의 인터페이스를 만드는 것과 네이버가 외부 원고를 받아주는 인터페이스가 있는 것은 별개다. 프로세스 통신으로 네이버 서버의 로그인·글쓰기 경로를 대체할 수는 없다.

| 방식 | 이 프로젝트에서의 역할 | 한계 |
| --- | --- | --- |
| 파일 내보내기/가져오기 | JSON/Markdown/이미지 묶음 전달, 다른 프로젝트 연동 | 네이버 업로드가 자동 완료되는 것은 아님 |
| 클립보드 지원 | 제목·본문·태그 복사, 이미지 순서 안내 | 복사 HTML 서식의 보존 보장 불가 |
| Playwright 브라우저 자동화 | 로그인된 편집기에 입력·사진 배치·임시저장 | 실제 DOM 확인 필요, 화면 변경·로그인 만료에 취약 |
| 확장 프로그램 | 현재 로그인 브라우저에서 사용자가 원고 채우기 실행 | 설치/권한/배포 관리 필요, 아직 미구현 |
| 로컬 도우미와 IPC | 웹/CLI의 구조화 원고를 로컬 브라우저 실행기로 전달 | 메시지 인증·크기 제한·원점 검사·작업 소유권 필요 |
| 화면 좌표 기반 RPA | DOM 접근 불가 시 최후의 보조 수단 | 해상도/창 위치/팝업에 매우 취약 |

추천 순서: 로컬 Playwright로 짧은 원고 임시저장 가능성부터 검증 → 자료/템플릿 자동 준비와 명시적인 실행 버튼 → 반복 사용이 필요해지면 로컬 도우미 또는 확장 프로그램 선택. 모두 동시에 만들지 않는다.

소수 사용자의 초기 UX:

자료 가져오기 → 출처/누락 확인 → 템플릿 초안 → 미리보기/검토 → 네이버 편집기에 채우기 → 임시저장 확인 → 작성자가 공개 판단.

브라우저 단계가 실패해도 완성 원고와 이미지 묶음을 내보내 사용할 수 있게 한다. '내보내기 완료', '편집기 입력 완료', '임시저장 확인', '공개 완료'를 따로 기록한다. 저장 응답이 끊기면 먼저 기존 초안 존재 여부를 확인하고 신규 생성은 반복하지 않는다. CAPTCHA나 추가 인증은 사용자에게 넘기며 비공개 엔드포인트 추측 호출을 기본 설계로 삼지 않는다.

서비스와 로컬 도우미를 나눌 때 사용자가 보는 서버 UI와 브라우저 로그인 위치를 명확히 표시한다. 네이버 비밀번호·쿠키를 서버로 수집하지 않는 방향을 우선한다. 원고 전달은 일단 사용자가 선택한 파일 또는 CLI로 시작할 수 있으며 소켓/HTTP 상시 수신 서버를 처음부터 요구하지 않는다.
